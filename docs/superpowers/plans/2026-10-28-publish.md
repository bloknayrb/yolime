# chore/publish: install yolime for daily use (v1, for review)

PR8 of `docs/plan.md`: "Publish script installing to `%LOCALAPPDATA%\Programs\Yolime`, a quoted Run-key path, and a README covering usage and known limits."

## Already true on main
- The Run value is quoted: `StartWithWindows.CommandFor` writes `"<exe>"`. Settings shows "another copy" when the value points elsewhere (`StartupStatus.OtherCopy`) and re-points it on Enable.
- Single instance: a second launch redirects to the first, which says "already running". **Its arguments are deliberately ignored**, so another process can't steer the running app.
- A Release or publish build can't contain E2E code (`Directory.Build.props` guards).

## Found while preparing (2026-10-28)
A plain `dotnet publish src/Yolime.App -c Release` leaves `Yolime.App.pri` out of the publish folder, though the build folder has it. This is a known pitfall when publishing unpackaged WinUI apps: the app's own resource index, which carries App.xaml's compiled resources, isn't copied. With `-p:EnableMsixTooling=true` it is published. Whether the published app then starts is checked in the Sandbox (below), not assumed.

## Changes

### 1. `EnableMsixTooling` in the App csproj
`<EnableMsixTooling>true</EnableMsixTooling>`, so publish carries `Yolime.App.pri`. `WindowsPackageType` stays `None`: still unpackaged, no MSIX.

### 2. `tools/install.ps1`
Runs under Windows PowerShell 5.1 and PowerShell 7.

**Build:**
- Runs `dotnet publish src/Yolime.App -c Release -o artifacts/publish`.
- Skipped with `-From <folder>`, which installs an existing publish folder (what the Sandbox test uses).

**Check the build before installing:**
- `Yolime.App.exe`, `Yolime.App.dll` and `Yolime.App.pri` exist.
- `Yolime.App.dll` contains none of the E2E-only markers (`--test-audio`, `yolime-main-e2e`). This is a second guard after the build-time one.

**Refuse while yolime is running:**
- Detected by a `Yolime.App` process whose path is under the install folder, or any `Yolime.App` process at all (a dev copy holds the single-instance key too).
- The script says "Exit yolime from the tray first" and stops.
- `-Force` stops the process instead, warning that a run in progress and the clipboard restore are lost. This keeps the no-arguments design: no `--exit` switch that another process could use.

**Install:**
- Copies to `%LOCALAPPDATA%\Programs\Yolime.new`.
- Renames the current `Yolime` to `Yolime.old`, then `Yolime.new` to `Yolime`, then deletes `Yolime.old`.
- If the second rename fails, `Yolime.old` is renamed back, so a failed upgrade leaves the old copy working.

**Start menu:** a `yolime` shortcut in `%APPDATA%\Microsoft\Windows\Start Menu\Programs` pointing at the installed exe.

**Start with Windows:**
- If a `yolime` Run value already exists, it's rewritten to the installed exe, quoted, so a start-with-Windows set up from a dev build follows the install.
- If none exists, nothing is added: it's the user's choice in Settings (or the wizard).
- Task Manager's `StartupApproved` switch is never touched.

**`-Launch`** starts the installed copy afterwards.

**Uninstall: `tools/install.ps1 -Uninstall`**
- Refuses while running (`-Force` as above).
- Removes the shortcut, removes the Run value only if it points into the install folder, and removes the install folder.
- **Leaves the user's data**: settings, history, the pending audio kept for Retry, logs, and the keys in Credential Manager. It prints where they are, and that tray > Reset removes them, so run it before uninstalling to remove everything. (A `-RemoveData` switch would duplicate Reset's careful wipe from a script; not worth it.)

### 3. README
Covers:
- install, upgrade and uninstall;
- the first run and keys;
- holding the key and cycling modes with Shift;
- the four modes, double-tap hands-free, paste-last (Win+Alt+V), the overlay and the preview, and History;
- Settings;
- **what is sent where**: audio to OpenAI or Groq, text and context to Anthropic. Logs never hold content;
- where data lives;
- the timing report.

**Known limits:**
- it's unsigned, so SmartScreen may warn and Smart App Control may block it;
- it can't paste into elevated windows (it copies instead);
- terminals and remote sessions get the text copied, not pasted;
- password fields are skipped;
- it's Windows 11 x64 only;
- the deferred items in the PR6, PR7 and hold-race PRs.

The status line stops saying "in development".

### 4. Sandbox install test, `tests/Install/run-install-test.ps1`
The host publishes, then maps the publish folder and `tools/install.ps1` read-only into a sealed Sandbox (no network, as in E2E). A test script inside the Sandbox, run with Windows PowerShell 5.1:
1. Seeds a `yolime` Run value pointing at `C:\dev\Yolime.App.exe`.
2. Runs `install.ps1 -From C:\pkg -Launch`. It checks:
   - the files are in `%LOCALAPPDATA%\Programs\Yolime`;
   - the shortcut exists;
   - the Run value is exactly `"<install>\Yolime.App.exe"`.
   - **The app is still running 20 s later, from the install path**, with its welcome window (main window title) up. This proves the published build starts, which is the `.pri` question.
3. Runs `install.ps1 -From C:\pkg` again while it's running: exits non-zero and leaves the files alone.
4. Runs `install.ps1 -From C:\pkg -Force`: the upgrade goes through and the old folder is gone.
5. Runs `install.ps1 -Uninstall -Force`: the folder, the shortcut and the Run value are gone, and `%APPDATA%\Yolime` is still there.

Results go to a results folder as JSON, which the host only reads.

## Not in this PR
- Code signing, an MSIX package, auto-update.
- Renaming the exe from `Yolime.App.exe`. The process name shows in Task Manager. Renaming it would change paths that the Run value and the existing tests depend on, for a cosmetic gain.

## v2 rulings (two reviews: platform, installer and security; UX and docs)

These replace the matching parts above where they differ.

1. **EnableMsixTooling is confirmed.**
   - The reviewer compared builds with and without it. It only switches PRI generation to MRT tooling and sets `GenerateAppxPackageOnBuild=false`.
   - The publish output differs by exactly `Yolime.App.pri`.
   - The PRI embeds `App.xbf`, so the loose file isn't needed.
   - The E2E build works with it.
   - CI gains a publish step: `tools/check-publish.ps1` asserts the `.pri` and the markers (ruling 2), so a later Windows App SDK bump can't drop the `.pri` unnoticed.
2. **The E2E-marker check searches UTF-16LE bytes.** C# literals are UTF-16 in the DLL, and an ASCII or 5.1 `Select-String` search passed a real E2E build. The markers are `--test-audio`, `yolime-main-e2e` and `--e2e`, matched whole, as in `ReleaseHasNoTestCodeTests`. They live in `tools/check-publish.ps1`, shared by install and CI. The Sandbox test proves the check can fail: installing from an E2E build must be refused.
3. **The running check is the real protection, not a courtesy.** Renaming the folder of a running exe succeeds, which would leave a mixed-version process.
   - Any `Yolime.App` whose path is under the install folder, or whose path can't be read, counts as running. The script refuses and prints that copy's path.
   - A copy running elsewhere (a dev build) isn't killed. The script warns that it holds the single instance, and skips the launch.
   - `-Force` first asks yolime to exit cleanly: it posts `WM_COMMAND` 3 (Exit) to the `yolime-tray` window, which the app already handles. Same-user processes can already terminate it, so this grants nothing new. Exiting cleanly restores the clipboard and removes the tray icon.
   - After 5 s it falls back to `Stop-Process`, then `WaitForExit`, then a re-check.
   - The small window between the check and the swap is a documented residual.
4. **The swap is made robust:**
   - At start, recover: if `Yolime` is missing and `Yolime.old` exists, rename it back.
   - Remove a stale `Yolime.new` and `Yolime.old` first, and abort if that's impossible.
   - Create `Yolime.new` empty and copy the publish folder's **contents** into it. (`Copy-Item -Recurse` nests when the destination exists.)
   - Verify `Yolime.new` itself (exe, dll, pri, markers).
   - Each rename and delete retries a few times with backoff (Defender scanning).
   - Deleting `Yolime.old` only warns, and the next run retries it.
   - Refuse if any of the three folders is a reparse point.
5. **Refuse to run elevated.** An admin `-Launch` would start an elevated yolime with an elevated hook. With over-the-shoulder UAC, the profile paths and HKCU would also be another user's.
6. **Order:**
   - Install: the Run value and the Start menu shortcut are written only after the swap succeeds.
   - Uninstall: renames the folder aside first, which proves nothing holds it. Then it removes the shortcut, the Run value and its `StartupApproved` entry (matching the app's own Disable), and deletes the folder.
   - "Points into the install folder" compares normalised full paths, case-insensitively, as a prefix match with a trailing `\`.
7. **Paths come from `GetFolderPath`**: `LocalApplicationData` and `Programs`, not environment variables.
8. **Launch by default** after an install or upgrade; `-NoLaunch` opts out. It is skipped (with a note) when another copy holds the single instance.
9. **Script hygiene:**
   - pure ASCII, no 7-only syntax;
   - `$LASTEXITCODE` checked after `dotnet publish`;
   - the publish folder emptied first;
   - Sandbox JSON written with `ConvertTo-Json -Depth 5` and UTF-8 without BOM.
10. **The script prints at the end:**
    - the install path and the Start menu entry;
    - the Start with Windows state ("re-pointed", or "off: Settings > General");
    - whether yolime is running;
    - the first-run hint: keys go in Settings > Keys, or the `YOLIME_ANTHROPIC_API_KEY` / `OPENAI_API_KEY` environment variables, which are read at start;
    - the Smart App Control state, read from `HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy\VerifiedAndReputablePolicyState`, as a warning when it's on or evaluating.
11. **Uninstall prints exactly what stays and how to remove it:**
    - `%APPDATA%\Yolime` (settings, prompts);
    - `%LOCALAPPDATA%\Yolime` (history.db, `pending\` voice recordings kept up to 7 days for Retry, logs);
    - the Credential Manager entries `yolime/<KEY>`.
    It also gives copy-paste `Remove-Item` and `cmdkey /delete:` lines, and recommends **Settings > Advanced > Reset yolime** before uninstalling. That is where Reset lives; the tray has no Reset. Reset also removes the Run value and exits, so no `-Force` is needed afterwards.
12. **README corrections from the code** (the UX review checked each against the source):
    - Reset is in Settings > Advanced.
    - The Claude key is `YOLIME_ANTHROPIC_API_KEY`: `ANTHROPIC_API_KEY` is ignored on purpose.
    - In terminals and remote sessions **only Reply** is copied instead of pasted. The other modes paste, with Shift+Insert in mintty and PuTTY.
    - Editors and terminals start in Prompt mode.
    - The preview is **Ctrl held at release** (not Shift as the original spec says), plus the per-mode "Always preview" settings.
    - Hold keys are Right Ctrl, Right Shift or Pause.
    - The hold rules: under 300 ms is discarded; any other key, click or scroll aborts; caps are 2 and 5 minutes; Esc; tap to cancel during processing.
    - Tray: the left click, the menu, and the icon legend.
    - History retention, and that Pause history keeps nothing.
    - Recordings are kept in `pending\` until transcription succeeds.
    - settings.json-only options, with a snippet.
    - The dev and installed copies share data and the single instance, so the wizard won't reappear on a machine that ran a dev build.
    - Plain-words known limits replace "the deferred items in PRs".
    - The execution-policy line: `powershell -ExecutionPolicy Bypass -File tools\install.ps1`, or pwsh.
13. **Sandbox test changes:**
    - Stage `artifacts\install-test\{pkg,tools,e2epkg}` as one read-only mapping, since a single file can't be mapped. Run it with `-ExecutionPolicy Bypass`.
    - Step 3 asserts the exe is unchanged (hash).
    - Step 4 relaunches and asserts it is the new copy, so step 5's `-Force` exercises the clean-exit path. Step 5 also asserts `%LOCALAPPDATA%\Yolime` survives.
    - Negative controls: installing from an E2E build is refused, and a copy with `Yolime.App.pri` deleted is *not* running after 20 s. The second shows the start check can see the bug.
14. **Not done:** an app icon (cosmetic), and a `-RemoveData` switch (the printed commands cover it).

## After the branch review

- **Ruling 12 was wrong about the preview.** The in-app help says "hold Ctrl as you let go", but a Ctrl press during a hold discards it, and the code previews on **Shift** held at release (the spec's gesture). Shift-down while recording also cycles the mode, so today a per-run preview can't happen without changing mode. That gets its own PR, `fix/preview-gesture`: per the spec, a Shift tap cycles and Shift held at release previews without cycling, and the Settings help text is fixed there. The README describes that behaviour, so **this PR merges after that one.**
- **The README now matches the code** on: what goes to Anthropic (the vocabulary and the style profile, never the app's name); the Reply click-wait (only for a read-only selection, up to 10 s); scrolling (Up, Down and Page keys only); hands-free Esc and app switching; retry-by-tap when double-tap is on; the tray labels; and terminal paste keys and line breaks.
- **Scripts:**
  - a failed rollback is retried, and the message says what happened;
  - `.uninstall` is reparse-checked and stray folders are cleaned;
  - only this session's copies count;
  - the Start with Windows line respects Task Manager's switch;
  - the launch check waits up to 15 s;
  - the other-copy warning shows with `-NoLaunch` too;
  - check-publish resolves relative paths.
- **Tests:**
  - the Sandbox test captures install.ps1's stderr as output, not as a terminating error;
  - the E2E-build refusal must name the test code (in CI too);
  - both `-Force` runs must have used the clean exit.
