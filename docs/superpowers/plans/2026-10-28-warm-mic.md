# feat/warm-mic: keep the microphone ready between holds (v1, for review)

The PR7 plan's item 6, which its v2 rulings moved to its own PR (`2026-10-28-latency.md`). Those rulings bind this plan:
- a gate in `OnData` before `Emit`;
- a fresh channel per hold, with `_pendingLength` reset;
- "ready for about 60 s after a hold", not always on;
- a reopen after device loss or resume;
- copy that names the mic indicator and Bluetooth's call-quality profile.

The rulings also asked to "measure key-down to first chunk per device first". This PR adds that measurement to the timing log, so the default can be decided on data. The setting ships **off**.

## Why
Opening a WASAPI capture costs 100–300 ms on a cold device, and around a second for a Bluetooth headset switching profile. The start cue already waits for the first buffer (PR7). So the cost isn't a lost syllable but a wait before speaking, and for people who don't wait, a clipped first word. A device kept open removes both, for the next hold.

## Design
**Core, all of it unit-tested:**
- **`MicReadiness`** decides whether the device should be open:
  - `HoldEnded(atMs)`: ready until `atMs + KeepMs`, with `KeepMs` = 60 s.
  - `HoldStarted()`: it's in use.
  - `Suspend(reason)`: lock, sleep, Pause hotkeys, the setting turned off, or the chosen mic changed. It closes now and stays closed until the next hold.
  - `Tick(nowMs)`: whether to close because the 60 s are up.
  - Pure, with an injected time.
- **`CaptureHub`** sits between a running device and the holds.
  - `Open(ILiveCapture source)` takes a running source.
  - `Begin()` returns a per-hold `ILiveCapture` with a fresh bounded channel and fresh chunking (`_pendingLength` = 0).
  - Buffers arriving with **no hold active are dropped in the callback**, before any copy or chunking: never buffered, logged, written or sent.
  - The hold's `Stop()` ends its channel only. The device stays open.
  - A device error (lost, access revoked) ends the active hold's channel with that error and marks the hub closed. The next hold opens cold.
  - `FirstAudio` completes at once for a hold on an already-running device.
- **`ICaptureDevice` doesn't change.** `ReadyMicDevice : ICaptureDevice` wraps a `CaptureHub`, `MicReadiness` and an inner "open a raw device" factory. The coordinator doesn't change at all.

**App:**
- **`WasapiDevice`**: the raw source becomes reusable: it delivers buffers to a callback until disposed. The existing per-hold `WasapiLive` behaviour stays when the setting is off.
- **AppHost wiring:**
  - `ReadyMicDevice` is used when `KeepMicReady` is on.
  - Session lock and logoff (`SessionEnded`), sleep (`SystemEvents.PowerModeChanged` Suspend), Pause hotkeys, a `MicDeviceId` change and turning the setting off all call `Suspend`.
  - The hook's 100 ms tick (or a 1 s timer) calls `Tick`.
- **Settings > General:** "Keep the microphone ready between holds".
- **Help text:** "For a minute after each hold the microphone stays open, so the next one starts at once and your first word isn't clipped. Meanwhile Windows shows that the microphone is in use, and a Bluetooth headset may stay in its lower-quality call mode. Nothing is recorded between holds."

**Measurement (both settings):**
- `RunTiming.MicFirstAudioMs`: key-down to the first buffer.
- `RunTiming.MicWasReady`: a bool.
- The timing report shows the p50 of `MicFirstAudioMs`, split by `MicWasReady`.
- Numbers and a bool only; the no-content test covers them.

## Tests
- **`MicReadinessTests`:**
  - ready for 60 s after a hold;
  - closes at 60 s;
  - a new hold within 60 s keeps it open;
  - each suspend reason closes it now;
  - off means never kept.
- **`CaptureHubTests`:**
  - buffers with no hold active are dropped and never reach a later hold;
  - each hold gets only its own audio;
  - a partial chunk from one hold never leaks into the next;
  - stop ends the hold, not the device;
  - a device error fails the active hold and closes the hub;
  - `FirstAudio` completes at once when warm.
- **`ReadyMicDeviceTests`:**
  - the first hold opens cold;
  - the second within 60 s reuses the device (one open);
  - after the 60 s, or a suspend, the next hold opens again;
  - a failed open still throws `AudioCaptureException`.
- **E2E (Sandbox).** The E2E's file mic is wrapped in the same `ReadyMicDevice` when the run is configured with `--test-keep-mic-ready`. Sandbox has no audio input, so WASAPI itself can't be exercised there.
  - `KeepMicReady_SecondHoldReusesTheMic`: two holds paste. The file mic's open count, exposed to the harness, is 1. A hold after a `Pause hotkeys` round trip opens it again.
- **Not testable here: the real WASAPI device staying open.** It needs a real microphone. It is verified by the timing log on Bryan's machine (`MicWasReady` = true, with `MicFirstAudioMs` near 0), and the PR says so.

## v2 rulings (three reviews: audio platform, privacy and UX, architecture and tests)

These replace the matching parts above where they differ.

**Sequencing: measure first, as the ruling says.** Two PRs:
- **PR A, `feat/mic-timing`:** the measurement only, on today's cold path.
- **PR B, `feat/warm-mic`:** the feature, built behind the setting (default off), so the data from PR A can decide whether anyone turns it on.

### PR A: measurement
1. **First-buffer time.**
   - `ILiveCapture` gains `long? FirstAudioAt`, a timestamp on the injected `TimeProvider`'s clock. It is stamped in `OnData` on the first buffer actually delivered: not on stop or error, and not when the `FirstAudio` continuation runs.
   - `WasapiDevice` takes the app's `TimeProvider`.
2. **Mic kind.** `ILiveCapture` gains `MicKind Kind`: `Unknown`, `Builtin`, `Usb` or `Bluetooth`. It comes from the endpoint's enumerator name (`BTHENUM`/`BTHHFENUM` is Bluetooth, `USB` is Usb, `HDAUDIO`/`INTELAUDIO` and the like are Builtin). The classifier is in Core and tested. It's an enum, never a name.
3. **Into the timing log.**
   - The coordinator stamps key-down on the same clock (`Capture.StartedAt`).
   - `RunRequest` carries a `Func<MicTiming?>`, read in the pipeline's `Finish`, because a cold Bluetooth first buffer can arrive after the pipeline started.
   - `RunTiming` gains `MicFirstAudioMs` (`long?`) and `MicKind` (`MicKind?`). Both are null for retries and re-runs, so those can't drag down the cold p50.
   - `RunTiming`'s comment notes that this field is measured from key-down.
4. **Report.** `tools/timing-report.ps1` prints the `MicFirstAudioMs` p50/p90 per mic kind, and skips nulls and older lines.

### PR B: warm mic (for after PR A)
5. **A push-style raw source in Core.**
   - `IRawCapture` delivers `(ReadOnlySpan<byte> pcm, long captureQpc, bool silent)` through a delegate, and errors through an event.
   - The chunker (100 ms chunks, RMS, the bounded channel, the drop count, the end flush) moves from `WasapiLive` into Core and is used by both paths. `WasapiLive` shrinks to the NAudio adapter and the HRESULT mapping.
   - The between-holds gate runs in the raw callback, before any copy: the ruling's "gate in OnData before Emit". The E2E file mic implements `IRawCapture` too.
6. **The hold's edges are cut by capture time (QPC), not arrival time.**
   - A hold takes the buffers captured from its key-down onward.
   - Stop records a mark. The capture thread then delivers what was captured before the mark, flushes the partial chunk and completes the channel itself (one writer), with a 200 ms fallback for a device that stops delivering.
   - Tests: a buffer captured before Begin but delivered after it; Stop flushing the partial chunk; a buffer after Stop reaching neither hold.
7. **`FirstAudio`, when warm, completes on the first buffer delivered to this hold** (about 10 ms), never at Begin.
   - If none arrives within 200 ms, or every buffer is flagged silent, the device closes and reopens cold for the same hold.
   - The same applies to an error before the hold's first buffer.
   - A stalled stream therefore never gets a "speak now" cue.
8. **Only a hold that reached Recording (300 ms) extends the minute.**
   - Taps, Right-Ctrl shortcuts and discards don't, so someone who uses Right Ctrl shortcuts all day doesn't keep the mic lit.
   - This needs one small signal from the coordinator (`Stop(wasDictation)`), so the "coordinator unchanged" claim is dropped.
9. **The 60 s close is `ReadyMicDevice`'s own timer** (`TimeProvider.CreateTimer`), with the dispose on the thread pool. It never runs on the hook thread: disposing the recorder joins NAudio's capture thread, and the low-level hook would time out.
   - One lock serialises open, Begin, close and suspend.
   - A suspend during a hold takes effect when the hold ends.
   - Test: with no external ticks, the device still closes by the deadline plus about 1 s.
10. **The per-hold handle** is idempotent for Stop and Dispose, and detaches with a compare-exchange only if it is still the active hold.
    - Test: disposing hold A after hold B began leaves B recording.
    - Test: dispose without Stop closes the gate.
11. **A stream that dies with no hold active closes silently:** no notice, no sound, no tray change. The next hold opens cold.
12. **Suspend triggers:**
    - `_tray.SessionEnded` (it already covers lock, both disconnects and `PBT_APMSUSPEND`; no `SystemEvents`);
    - `_tray.PauseChanged`;
    - `OnSettingsChanged` (the setting turned off, or the mic changed);
    - an `IMMNotificationClient` default-device or device-state change;
    - `AppHost.Dispose` disposes the device.
    A single `ReadyMicDevice` reads the setting at each Start.
13. **Copy** (the toggle sits directly under the Microphone row):
    - Label: "Keep the microphone open for a minute after each hold".
    - Help: "For a minute after each hold, the microphone stays open so the next hold starts without waiting for it. Meanwhile Windows shows that yolime is using the microphone, and a Bluetooth headset may stay in call mode, so music through it sounds worse (and briefly drops out when it closes). Everything heard between holds is thrown away as it arrives: nothing is kept, shown or sent. Pause hotkeys closes the microphone at once."
    - The tray tooltip gains "· microphone open" while it's warm.
    - README: a usage bullet, a "what is sent where" line, and a known limit (an exclusive-mode app can't take the mic while it's warm).
14. **Timing:** `MicStart` (`Cold`, `Warm` or `WarmReopened`) joins PR A's fields.
15. **E2E:**
    - Turned on through `"keepMicReady": true` in a separate app launch with its own data folder, so the cold path keeps its coverage.
    - AppHost wraps whatever raw source it's given.
    - Assertions:
      - the second hold reuses the source;
      - Pause hotkeys reopens it;
      - a hold's `AudioBytes` match its length, not its length plus the gap (the leak check);
      - a tap doesn't extend the minute.

## Rulings made while building PR B

- **The cold path is unchanged (deviates from ruling 5).**
  - With the setting off, holds use today's `WasapiLive` as before; only the kept-ready path uses the Core gate and chunker.
  - Why: the default path carries no new risk, and PR A's cold-start baseline stays comparable.
  - Cost if wrong: two chunkers to maintain.
- **A device error before a warm hold's first buffer fails that hold; it doesn't reopen it (narrower than ruling 7).**
  - The 200 ms warm check (no buffer, or only buffers flagged silent) does reopen it for the same hold.
  - Cost if wrong: an error in the first 200 ms of a warm hold shows "microphone lost" where a reopen might have saved it. The next hold opens cold.
- **QPC capture times are converted to Stopwatch ticks** (`qpcPosition` is in 100 ns units). If the device reports none, the arrival time is used.
- **A tap within an earlier dictation's minute leaves that minute as it was.** It neither extends it nor ends it.
