# PR7 `perf/latency` implementation plan (v1, for multi-angle review)

**Spec:** `docs/plan.md`, PR list item 7, and "Latency / cost targets".

The spec asks for:
- pre-warmed connections;
- streaming STT while the key is held;
- LLM streaming into the overlay preview;
- an optional warm mic;
- silence trimming.

Each change is measured against the PR1 timing log.

Targets:

| Mode | Time to paste |
|---|---|
| Dictate | 0.4–1 s |
| Prompt | 2–4 s, with the first preview text in under 1.5 s |
| Reply | 1.5–3 s |

## What we know now

- **The timing log** (`timings-*.jsonl`) records per-stage milliseconds, audio bytes, character counts, the outcome, and whether STT opened a cold connection (`SttResult.ColdConnection`).
- **Every E2E run shows an Output stage of about 5,000 ms** for paste deliveries, for Dictate, Prompt and Reply alike. No wait in the code accounts for it:
  - `ModifierWait` is 3 s;
  - the UIA snapshot budget is 300 ms;
  - `Paste` returns as soon as `SendInput` does;
  - the restore runs in the background.

  It may be specific to the Sandbox (the harness holding the clipboard open, so `SaveAsync` retries), or it may be real. **The first task is to measure it, not guess.**
- **Overlay streaming already exists:** PR4 added `DeltaArrived`, and `OverlayProgress` forwards rewrite deltas, so Claude's text already streams into the notch. This PR only measures time to first delta and adds it to the log.

## Plan

1. **Instrumentation (Core, TDD).**
   - `RunTiming` gains the Output sub-stages as integers:
     - `ModifierWaitMs`;
     - `TargetSnapshotMs`;
     - `ClipboardSaveMs`;
     - `ClipboardSetMs`;
     - `PasteSentMs`.

     It also gains `FirstDeltaMs` (key release to the first rewrite delta) and `SttUploadBytes`.
   - The executor reports them through a small `IOutputTimings` sink; the pipeline writes them into the run's timing.
   - Numbers only: the "no content in logs" test covers the new fields.
   - A Core `TimingReport` reads `timings-*.jsonl` and prints p50/p90 per mode and per stage. It is used by an E2E latency summary and by a `--timing-report` switch in the E2E harness. The switch runs only under `YOLIME_E2E`.
2. **Find and fix the Output stall** using those numbers, in the Sandbox. A fix that is real on a desktop (for example a clipboard save retrying against a slow owner) goes in this PR. A pure Sandbox artefact gets a note, with the harness fixed instead.
3. **Pre-warmed connections.**
   - `SocketsHttpHandler.PooledConnectionIdleTimeout` goes to 5 minutes, and `KeepAlivePingDelay`/`Timeout` keep HTTP/2 alive.
   - **At key-down**, if the STT host's pool hasn't been used for more than 4 minutes (tracked per host), a background warm request is sent: `HEAD https://api.openai.com/v1/models` (Groq's equivalent, or the custom base URL) with **no key**. A 401 is fine, because the point is the TLS connection. The Claude host gets the same, only for Prompt and Reply holds, or when the hold cycles into them.
   - The warm request is pinned like every other request, sends no key and no content, and is logged as `ConnectionWarmed` with its milliseconds.
4. **Silence trimming.**
   - Before upload, leading and trailing silence beyond 250 ms is trimmed from the PCM. It uses the same RMS gate as `SpeechGate`, with 100 ms chunks and `SilenceRms`.
   - Smaller uploads mean faster STT. The raw recording on disk is kept untrimmed, because Retry needs the original.
   - Core function `SilenceTrim.Trim(pcm, threshold)`, with tests.
5. **Streaming upload while the key is held.**
   - OpenAI and Groq transcription is request/response; true streaming STT (the OpenAI Realtime WebSocket) is a different protocol and cost model, so it is **out of scope**.
   - Instead, the multipart upload starts at key-down, with a WAV header of unknown length (`0xFFFFFFFF` data size, which both APIs accept for PCM WAV: **to verify with a live test under `YOLIME_LIVE`**). Audio chunks are written to the request stream as they arrive, and the request completes at key-up. The upload then overlaps the speech, and key-up costs only the server's processing.
   - Behind a setting, `StreamingUpload` (default **on** if the live test passes, **off** otherwise). It falls back to the batch path on any error before the first byte of the response.
   - Silence trimming then applies only to the leading silence, since trailing silence is already sent. Trailing trimming stays for the batch path.
6. **Optional warm mic** (setting `KeepMicReady`, default **off**).
   - While on, the WASAPI capture stays open between holds, so key-down needs no device open (measured at 100–300 ms on cold devices).
   - Windows then shows the microphone-in-use indicator all the time. The Settings copy says so plainly.
   - Audio between holds is discarded in the callback: never buffered, written or sent.
   - It is suspended on lock, sleep and Pause hotkeys.
7. **Carry-overs from PR5/PR6 that affect latency or lost work:**
   - **Toast mid-hold:** check whether a toast banner during a hold fires `EVENT_SYSTEM_FOREGROUND` and discards the recording. If so, ignore foreground changes to shell notification windows.
   - **Tap-to-retry race:** a 1.5 s hold that began right after a cancelled run was taken as a tap and fired Retry. Find the cause; the retry must come only from a real short tap.
   - **Paste-last first paste:** it was intermittently copied. Its log line now names the reason.
8. **E2E latency check.** A Sandbox scenario dictates five times and asserts p50 Output < 1,500 ms and STT (fake) + rewrite (fake) overhead < 300 ms. It reports the per-stage medians to `latency.json` in the results. The real targets are verified on Bryan's machine with the live keys, not in CI.

## Out of scope
- A WebSocket realtime STT provider.
- Changing models.
- Batching LLM calls.

## Review focus
- Whether the unknown-length WAV upload is safe with both providers, and its failure and fallback modes.
- Whether the keyless warm request is safe (key leakage, cost, rate limits).
- The privacy cost of the warm mic and whether the copy states it honestly.
- Whether the instrumentation keeps logs content-free.
- Whether trimming can cut speech: soft starts, a breath, a quiet trailing word.

## v2 rulings after four reviews (platform, UI/UX, security, product). These override the text above.

**Scope.** PR7 is measurement plus the safe wins. Three items move out to their own PRs, each with the constraints the reviews set:

- **Streaming upload** moves to its own PR and is built **only if measurement shows upload time matters**.
  - At 32 KB/s, a 10 s clip is about 320 KB, so the upload probably costs tens of ms, while server processing dominates.
  - If it is built, it must meet all of these:
    - The request opens only once the hold is committed and the snapshot is known not to be a password field. Audio is buffered until then.
    - It starts at the first speech chunk, with about 250 ms of pre-roll.
    - A discard, Esc or NoSpeech aborts the request through its token. It never completes the body.
    - The live test checks the transcribed `duration` (verbose_json), not only a 200, and checks for 411.
    - It has its own byte and time ceiling.
    - It runs over HTTP/2, or it doesn't warm.
- **Warm mic** moves to its own PR. It doesn't shorten time to paste; it prevents clipped first syllables. Measure key-down to first chunk per device first. If it is built:
  - a gate in `OnData` before `Emit`;
  - a fresh channel per hold, with `_pendingLength` reset;
  - "ready for about 60 s after a hold" rather than always on;
  - a reopen after device loss or resume;
  - copy that names the mic indicator and Bluetooth's call-quality profile.
- **Carry-over correctness bugs** move to their own PR, `fix/hold-races`, after this one (the one-concern rule):
  - a toast mid-hold;
  - the tap-to-retry race;
  - paste-last copying.

**In PR7, in order of expected win:**

1. **Probe first, then instrument.**
   - First, a temporary Stopwatch log line around every await on the Output path, run in the Sandbox to find the roughly 5 s stall. Candidates: `FlushCoreAsync` waiting on the previous run's restore (`WaitForIdleAsync`'s `SendMessageTimeout`, up to 2 s, which can't be cancelled once running); clipboard open retries (up to about 1.27 s for each of three opens); `GetClipboardData` blocking on a delayed-render owner; a modifier released just before the 3 s wait ends.
   - Then permanent `RunTiming` integers:
     - `FlushMs` and `GateWaitMs`;
     - `ModifierWaitMs` and `TargetSnapshotMs`;
     - `ClipboardOpenMs`, `ClipboardOpenAttempts`, `ClipboardSaveMs` and `ClipboardSetMs`;
     - `PasteSentMs` and `HistoryWriteMs`.
   - Plus a separate `RestoreTiming` event (`WaitForIdleMs`, `RestoreMs`, `TargetReadMs`).
   - Model ids go in as tags: the rewrite model and the STT provider and model. They aren't content.
   - `NewConnection` becomes per request, not a process-wide counter.
   - There's no `FirstDeltaMs`: `RewriteFirstTokenMs` already covers it.
   - Every new field is a number or an enum tag, covered by the no-content test.
2. **Fix the stall** that step 1 finds.
   - If the cause is real on a desktop, the fix is the product's.
   - If it's a Sandbox artefact (the harness polling the clipboard), the harness gets fixed, and that's noted.
3. **Delayed rendering for the paste**, which the PR2 note set aside for this PR.
   - The paste text is offered with delayed rendering. `WM_RENDERFORMAT` says when the target actually reads it.
   - The restore runs after that read plus a short grace period, with the current idle-plus-800 ms rule as the fallback timeout.
   - This stops a slow app (Outlook, Electron) pasting the old clipboard, which is worse than any latency.
   - Paste-to-read ms is logged.
   - The Done card shows when the paste is sent.
4. **Warm both hosts on every hold.**
   - At key-down, for every mode (Dictate calls Haiku for 12 words or more), each host gets a keyless `HEAD` if its last request finished more than N seconds ago. N is 30 s to start, tuned with `NewConnection`.
   - At most one warm-up in flight per host.
   - It is built from a bare `(Uri, host)` pair, never from `SttEndpoint`, which carries the key. Pinned with `Expect`. A custom endpoint is warmed only when its URL is valid.
   - A test asserts that warm requests carry no `Authorization` or `x-api-key` header.
   - No pool tuning: the client is on HTTP/1.1, where the keep-alive ping settings do nothing.
5. **The mic cue follows real audio.**
   - The start sound and Listening play on the first audio buffer, not at the 300 ms mark.
   - If no buffer has arrived by 300 ms, the notch shows "Mic starting…".
   - This stops first words being clipped by people who wait for the cue.
6. **Silence trimming** (modest: fewer hallucinations on silence, a little less server time).
   - It trims only stretches of silence longer than about 1 s.
   - It uses 0.5× `SilenceRms`, with a 450 ms pad on both sides.
   - The gate still runs on the untrimmed stream, so NoSpeech is unchanged.
   - The Retry path trims the same way.
   - The fixtures include a soft start and a quiet trailing "thanks".
7. **Timing report for Bryan:** `tools/timing-report.ps1` reads `%LOCALAPPDATA%\Yolime\logs\timings-*.jsonl` and prints p50 and p90 per mode, stage, model and provider. It runs in his release setup and is content-free. The acceptance check is about 20 live runs per mode against the target table.
8. **E2E regression guard:** a Sandbox scenario that dictates five times and asserts p50 Output under 1,500 ms. That is a regression guard, not target verification.

**Notes:**
- Provider choice for Dictate (Groq vs OpenAI) is a decision for Bryan once the live numbers exist.
- Thinking and effort settings are already correct (Haiku has thinking disabled, Sonnet uses `between_tools`), so that risk is closed.

## After the branch reviews

Two branch reviews (correctness and platform; security, privacy and UX) led to these changes:

- **Delayed rendering is reverted out of PR7 into its own PR.** It put every app's paste behind yolime's UI thread, so a stall there (the exit flush, a heavy window load) would hang another app's paste for about 5 s. Its success check on `SetClipboardData(fmt, NULL)` may also be wrong, which would leave it silently off. Whether a render changes the clipboard sequence number, which decides whether the restore still runs, is unverified. And it widened the window in which a password manager's clear timer could miss its own copy. The new PR needs:
  - a dedicated clipboard-owner thread;
  - a success check based on `GetLastError`;
  - a Sandbox check of the sequence number and WM_CLIPBOARDUPDATE around a render;
  - no extra wait when the saved clipboard is a password manager's;
  - logging of paste-to-read time.
- **`NewConnection` is per request** (set by the connect callback), so a warm-up opening a connection at the same moment no longer marks a real request cold.
- **The timing log** now records the uploaded bytes after trimming (`SttUploadBytes`) and the rewrite model (an enum, since logs hold no strings), and the report groups by model.
- **Trimming** keeps 400 ms before the speech and 1 s after it, so a mumbled last word after a pause survives.
- **The warm-up** skips a host with no key configured.
- **The start cue** fires on the first buffer, with a 2 s cap.
- **The breakdown table** is bounded.

**Still deferred:**
- The "Mic starting..." notch text (the start sound already waits).
- `ClipboardOpenMs` and attempts, and `HistoryWriteMs`.


## Streaming upload: measured, then built (2026-10-28)

The first measurement used the default socket send buffer and understated the upload: 0–1 ms for 108 KB, because the body sat in the kernel. With an 8 KB send buffer (`LiveUploadShareTests`), on a warm connection, the upload was:
- about 6% of the call at 3.4 s (35–45 ms of 560–710 ms);
- about 22% at 30 s (200–245 ms of 840–1155 ms).

That met the ruling's bar. A live probe showed OpenAI accepts a chunked, unknown-length WAV and hears all of it.

It's built in `feat/streaming-upload` (see `2026-10-28-streaming-upload.md`), default off, because it changes what a discarded hold sends.
